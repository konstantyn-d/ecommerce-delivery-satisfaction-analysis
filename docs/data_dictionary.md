# Data dictionary

Source: [Brazilian E-Commerce Public Dataset by Olist](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)
(Kaggle, licence CC BY-NC-SA 4.0). Nine CSV files, loaded unchanged into the `raw` schema of a DuckDB
database by [`sql/00_load_raw.sql`](../sql/00_load_raw.sql).

Every count on this page comes from [`docs/profiling_report.md`](profiling_report.md), which is generated by
[`notebooks/00_data_profiling.py`](../notebooks/00_data_profiling.py). Column meanings follow the dataset
documentation on Kaggle. This page describes the data **as delivered**; cleaning decisions are recorded in
`docs/decision_log.md` (Phase 1).

## 2. Relationships

```
                         raw.customers
                         (customer_id)
                               | 1
                               | exactly 1 order per customer_id
                               | 1
 raw.order_payments  n ---- 1  raw.orders  1 ---- n  raw.order_reviews
 (0..29 per order)             (order_id)            (0..3 per order)
                               | 1
                               | 0..21 items per order
                               | n
 raw.products  1 ---- n  raw.order_items  n ---- 1  raw.sellers
 (product_id)                                       (seller_id)
       | n
       | 1
 raw.category_translation
 (product_category_name)

 raw.customers.customer_zip_code_prefix ..> raw.geolocation.geolocation_zip_code_prefix
 raw.sellers.seller_zip_code_prefix     ..> raw.geolocation.geolocation_zip_code_prefix
 (dotted = lookup only: the zip prefix is NOT unique in geolocation, so a direct join multiplies rows)
```

Observed cardinalities (distinct key values):

| Child → parent | Orphans in child | Parents without child | Max children per parent |
|---|---|---|---|
| `orders.customer_id` → `customers` | 0 | 0 | 1 |
| `order_items.order_id` → `orders` | 0 | 775 orders have no items | 21 |
| `order_payments.order_id` → `orders` | 0 | 1 order has no payment | 29 |
| `order_reviews.order_id` → `orders` | 0 | 768 orders have no review | 3 |
| `order_items.product_id` → `products` | 0 | 0 | 527 |
| `order_items.seller_id` → `sellers` | 0 | 0 | 2,033 |
| `products.product_category_name` → `category_translation` | 2 categories | 0 | 3,029 |
| `customers.customer_zip_code_prefix` → `geolocation` | 157 zip prefixes | not relevant | 142 |
| `sellers.seller_zip_code_prefix` → `geolocation` | 7 zip prefixes | not relevant | 49 |

What this means for the model (Phase 2):

- **Referential integrity is clean**: no item, payment or review points to an order that does not exist.
- **An order is not tied to one seller**: 1,278 orders contain items from more than one seller. Seller and
  category analysis therefore needs an item-level fact table, not just an order-level one.
- **A person is not `customer_id`**: 99,441 `customer_id` values map to 96,096 `customer_unique_id` values;
  2,997 people have more than one order. Repeat-purchase analysis must use `customer_unique_id`.
- **Reviews are not 1:1 with orders**: 547 orders have more than one review and 789 `review_id` values are
  linked to more than one order. A rule for "the review score of an order" is needed before joining.

## 3. Columns

### raw.orders — one row per order

| Column | Meaning | Type | Example | Known issues |
|---|---|---|---|---|
| `order_id` | Unique identifier of the order | VARCHAR | `e481f51c...` (32-char hash) | None. Unique, no nulls. |
| `customer_id` | Link to `raw.customers`. A new value is issued for every order | VARCHAR | `9ef432eb...` | Not a person identifier (see `customer_unique_id`). |
| `order_status` | Current state of the order | VARCHAR | `delivered` | 8 values: delivered 96,478; shipped 1,107; canceled 625; unavailable 609; invoiced 314; processing 301; created 5; approved 2. |
| `order_purchase_timestamp` | When the customer placed the order | TIMESTAMP | 2017-10-02 10:56:33 | Range 2016-09-04 to 2018-10-17, but the edges are almost empty: 2016-09 to 2016-12 hold 329 orders in total (none in 2016-11); 2018-09 and 2018-10 hold 20 orders, none delivered. Complete months: 2017-01 to 2018-08. |
| `order_approved_at` | When the payment was approved | TIMESTAMP | 2017-10-02 11:07:15 | 160 nulls (0.16%). |
| `order_delivered_carrier_date` | When the seller handed the order to the carrier | TIMESTAMP | 2017-10-04 19:55:00 | 1,783 nulls (1.79%), expected for orders that never shipped. |
| `order_delivered_customer_date` | When the customer actually received the order | TIMESTAMP | 2017-10-10 21:25:13 | 2,965 nulls (2.98%). 8 orders are `delivered` without this date; 6 `canceled` orders have one. |
| `order_estimated_delivery_date` | Delivery date promised to the customer at purchase | TIMESTAMP | 2017-10-18 00:00:00 | No nulls. Always midnight: it is a date, not a time. This matters for the delay definition (Phase 2). |

### raw.order_items — one row per unit sold

| Column | Meaning | Type | Example | Known issues |
|---|---|---|---|---|

## 4. Issues handed over to Phase 1

These are observations only. Each one gets a decision (exclude / fix / keep and flag) in `docs/decision_log.md`.

| # | Issue | Size | Why it matters for this project |
|---|---|---|---|
| 1 | Orders not delivered | 2,963 of 99,441 orders have a status other than `delivered` | Delay and on-time metrics only exist for delivered orders. |
| 2 | Delivered orders without a delivery date | 8 | Delay cannot be computed. |
| 3 | Canceled orders with a delivery date | 6 | Status and timestamps contradict each other. |
| 4 | Incomplete months at both ends of the period | 329 orders in 2016; 20 orders in 2018-09/10 | Monthly trends would show false drops. |
| 5 | Orders without items | 775 | No order value, seller or category. |
| 6 | Order without payment | 1 | Minor; only relevant if payments are used. |
| 7 | Several reviews per order | 547 orders | Need one score per order to avoid double counting. |
| 8 | One `review_id` on several orders | 789 `review_id` values | The same review text would count for several orders. |
| 9 | Orders without a review | 768 | Excluded from satisfaction metrics; check whether they are mostly late or undelivered orders (selection bias). |
| 10 | Products without a category | 610 products | Category analysis needs an "unknown" bucket. |
| 11 | Categories without a translation | 2 | Easy fix: translate by hand. |
| 12 | Implausible `shipping_limit_date` | 4 rows after 2018-12-31 | Only relevant if seller dispatch delay is analysed. |
| 13 | Zero or extreme prices, freight, payments, weights | to be quantified | Can distort averages. |
| 14 | Geolocation duplicates and outliers | 261,831 duplicate rows; 42 rows outside Brazil; 157 customer and 7 seller zip prefixes missing | Only relevant if distance is analysed. |
